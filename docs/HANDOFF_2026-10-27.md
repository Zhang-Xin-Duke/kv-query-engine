# Handoff: rerun KV engine evaluation on the new workstation

Updated: 2026-10-27. The user is moving to a desktop with an RTX 5090 and also wants this project tested on that machine.

## Project and scope

Repository: https://github.com/Zhang-Xin-Duke/kv-query-engine

Name: High-Performance KV Query Engine for Read-Heavy Workloads.

The current engine is a CPU C++20 implementation. Its performance depends on the desktop CPU, cache, RAM and memory latency; it does not use the RTX 5090. Record the actual CPU/RAM rather than attributing query gains to the graphics card.

Read `README.md`, `docs/ARCHITECTURE.md`, `docs/BENCHMARKS.md`, `docs/SIMD_EVALUATION.md`, `docs/INLINE_EVALUATION.md` and `docs/VALIDATION.md` before modifying code.

## Implemented mechanisms

- Builder-side collision resolution: bidirectional nearby-slot search, relocation and relative-chain repair.
- Fixed 16-byte index nodes and contiguous external values with preallocated storage.
- Values of 0–6 bytes can be inlined within the same node, selected by packed layout tags; external-only mode remains available for a paired comparison.
- Immutable snapshots and one snapshot owner per result batch retain returned value views.
- Scalar, lookahead prefetch, AMAC and two-key SIMD probing with residual-state refill and ordered results.
- Native x86 SIMD is currently SSE2; ARM64 uses NEON; portable fallback is available. Do not call this AVX-512 or GPU acceleration.
- Checked snapshot persistence, CLI, correctness tests, sanitizer configurations and Linux CI.

## Existing measured baseline

The checked-in benchmark results were measured on a Duke Linux course server on 2026-10-24: Intel Xeon E5-2440 v2, roughly 16 GB RAM, GCC 11.4, SSE2, single-threaded and pinned to an allowed CPU. The reports record exact conditions and source/binary hashes.

For the published one-million-record, 32-byte-value, batch-1024 workload, SIMD/32 reached 22.13 Mkeys/s: 1.45× the compact scalar path and 3.78× `std::unordered_map`. This is a specific baseline workload, not a general guarantee.

Small-value inlining has paired tests, including larger 1M/4M/8M-record working sets. Benefits vary; the mixed-value case includes a regression. Preserve the original reports and figures when adding new desktop results.

## Run on the new machine

1. Detect OS, compiler, CPU topology/allowed affinity, RAM and cache sizes. Use a 64-bit POSIX environment with GCC/Clang C++20 and CMake. Linux/WSL2 is the straightforward path on a Windows desktop; existing persistence and runner code assume POSIX.
2. Build a fresh Release tree and run correctness checks before timing:

```bash
cmake -S . -B build/release -DCMAKE_BUILD_TYPE=Release
cmake --build build/release -j
ctest --test-dir build/release --output-on-failure
```

The existing suite has 11 CTest groups; verify the actual collected tests and their results.

3. Choose an allowed logical CPU based on the desktop topology. On a hybrid CPU, identify the core type and use the same selected core for every comparator. Do not assume logical CPU 0 is permitted or representative.
4. Run the standard, paired-inline and larger-working-set suites into new files. Replace `<allowed-cpu>` with the chosen logical CPU:

```bash
bash bench/run_linux.sh bench/results/desktop-standard <allowed-cpu> standard
bash bench/run_linux.sh bench/results/desktop-inline <allowed-cpu> inline
bash bench/run_linux.sh bench/results/desktop-inline-scale <allowed-cpu> inline-scale
```

The runner records environment and source/binary hashes and executes correctness checks. The suites use three independent processes and three rounds, matching query inputs and checksums across strategies. Keep the baseline compiler flags (`-O3 -DNDEBUG`, no `-march=native`) for a comparable primary run. Label any host-native build separately.

5. Use sufficient working sets to exceed the new CPU's last-level cache. The existing inline scaling suite reaches 8M records; extend the matrix only after checking RAM headroom, and keep query counts/comparison conditions matched. Do not cause swapping just to make a workload larger.
6. Compare unordered_map, Scalar, Prefetch, AMAC and SIMD across batch sizes and hit distributions. Report throughput and batch P50/P95/P99; batch latency is not per-key latency. Compare inline/external modes within each matched process.
7. Save raw JSON, generated Markdown, environment, hashes, repeated-run variation and any regressions. Update English README with an intuitive results figure near the front and clearly label desktop versus historical server data.
